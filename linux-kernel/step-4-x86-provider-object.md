# Step 4 generated x86-64 provider object

## Outcome

This is the fourth implementation increment of Step 4. From a checked systems
program, the compiler can now generate a deterministic, relocatable ELF64
x86-64 provider object without source assembly or an external assembler. A
private typed instruction model encodes the closed initial machine operations;
source cannot name instructions, registers, encodings, symbols, or sections.

The generated object contains:

- a provider text section with the sealed polled-port output, breakpoint,
  interrupt-return, and fatal-halt primitives;
- a `NOBITS` bootstrap-storage section whose size and alignment come from the
  checked storage descriptor;
- defined linkage symbols for those generated facilities; and
- a valid ELF note carrying the provider, target, board, CPU, data-layout,
  object, relocation, code-model, and storage identities.

The object is closed: it has no undefined symbols or relocations. Generation is
derived from the provider plan and produces identical bytes for identical
checked input.

## Boundary and remaining work

This increment physically encodes only the primitive facilities needed by the
current checked root and reserves its bootstrap storage. The monotonic storage
state machine remains the architecture-independent checked/reference model; it
is not yet emitted as linked runtime code. Entry and fault adapters, a linked
kernel ELF, canonical map/debug/provenance outputs, atomic publication, a boot
container, and QEMU evidence also remain absent.

Consequently, `x86_64-unknown-none` remains model-only in target discovery and
the ordinary compiler publication path still rejects it before output. The
object generator is an internal staged backend boundary, not a newly qualified
CLI artifact type.

## Validation and risk

Focused structural tests parse the generated bytes and prove the ELF class,
architecture, relocatable kind, deterministic output, section kinds, exact
storage size/alignment, complete note identity, absence of hosted Linux
identity, absence of relocations and undefined symbols, and the exact generated
instruction sequences. The full compiler library and repository traceability
tests cover integration with the preceding semantic, storage, and provider-plan
increments: all 184 compiler library tests and all four core-language coverage
tests pass. The changed compiler path also passes strict Clippy after allowing
only the crate's four unchanged baseline findings, and formatting checks are
clean.

Risk remains high because a wrong encoding or ABI assumption executes with
machine privilege. The implementation confines encodings to a private typed
provider model, maps only a fully checked plan, structurally inspects every
emitted facility in tests, and does not qualify or publish the target.
